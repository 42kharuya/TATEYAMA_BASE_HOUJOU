# WORKFLOW：公式WebサイトをAI駆動で作る進め方（MVP/1週間）

目的：公式サイトを **1週間で公開**。まずは「予約導線が分かりやすい・信頼できる・スマホで見やすい」を満たす。

参照（ソースオブトゥルース）

- 別荘基本情報がある場合：docs/INFO.md（ただし、このドキュメントは“一般的な工程”で記述）
- 追加メモ：このファイル（docs/WORKFLOW.md）

## 1. 企画（誰に・何を約束するか）

ここがブレると「ページ構成」「デザイン」「コピー」が全部ブレる。

- 想定ユーザー：例）ファミリー、友人グループ、アクティビティ目的 など
- 提供価値（約束）：例）清潔、アクセス、設備、体験、価格の分かりやすさ など
- 競合との差別化：例）屋上/設備/立地/体験 など

成果物（ファイル名：まとめる内容）

- docs/CONCEPT.md：ターゲット/提供価値/差別化/コンセプト文
- docs/COPY.md：キャッチコピー案（短い案を3つ）＋予約CTA文言案
- docs/DECISIONS.md：意思決定ログ（何を/なぜ/いつ決めたか、影響範囲）

最初のプロンプト（コピペ用）

```

目的：貸別荘の公式サイトを1週間で公開。予約導線が明確で、信頼できて、スマホで見やすいこと。
制約：根拠のない数値（徒歩◯分など）や断定は作らない。不明点があれば最大3つだけ質問してから進める。

1) docs/CONCEPT.md：ターゲット、提供価値、差別化、コンセプト文（1文）、トーン（3語）
2) docs/COPY.md：Heroのキャッチコピー案3つ、サブコピー案、予約CTA（ボタン文言）案
3) docs/DECISIONS.md：今回決めるべき意思決定項目のリスト（未決なら空でOK）

入力が不足している場合は、最初に質問を提示してください。
```

## 2. 要件定義（MVPの範囲を決める）

「作らないもの」も決めるのが要件定義。

受け入れ条件（MVP）

- スマホで破綻なく読める（主要ブラウザ）
- 予約ボタンが常に見つけやすい（ファーストビュー/ページ下部）
- 料金・キャンセルポリシー・アクセスが明確
- 画像が重すぎず、表示が遅くならない
- 根拠のない数値（徒歩◯分など）を掲載しない（不明は「要確認」）

MVPでやらない例（後回し）

- 料金シミュレーター、会員/ログイン、問い合わせフォームのDB保存
- Google Maps APIを使ったカスタムマップ（まずは埋め込みでOK）

成果物（ファイル名：まとめる内容）

- docs/REQUIREMENTS.md：MVPの範囲（やる/やらない）＋受け入れ条件（AC）
- docs/RISKS.md：詰まりやすい点（不確定情報、素材不足、法務/プライバシー等）と対策

最初のプロンプト（コピペ用）

```
あなたはシニア相棒エンジニア兼プロダクトエンジニアです。
目的：貸別荘の公式サイトMVPを1週間で公開。
制約：根拠のない数値は作らない。不明点は最大3つだけ質問。

次の成果物をMarkdownで作成してください。
1) docs/REQUIREMENTS.md：MVPのゴール/非ゴール、ページ構成（1ページLP or 複数ページ）、受け入れ条件（AC）、外部リンク（予約/地図）
2) docs/RISKS.md：公開までに詰まりそうなリスクと対策（予約URL未確定、素材不足、確定情報不足、プライバシー等）

前提の候補（仮置きは禁止）：予約は外部リンク。
```

## 3. コンテンツ準備（最短で詰まるポイント）

先に素材が揃うと実装が速い。

- 予約導線：予約ページURL（未確定なら「後で差し替え」前提で仮URL管理）
- 写真：Hero用の横長高画質、室内/設備/屋上/周辺（権利クリア済みのもの）
- ロゴ：あればSVG/PNG、なければ当面テキスト表記
- 確定情報：住所/チェックイン/チェックアウト/駐車場/利用ルール
- 料金表・キャンセル規約：必ず一次情報に基づく（不明は「要確認」）
- 注意：徒歩◯分などの数値は根拠がない限り書かない（仮置きしない）

このプロジェクトの決定（運用ルール）

- 予約/問い合わせURLが未設定の間は、CTAを「準備中」で表示してリンク無効（クリック不可）
- 画像素材は手元写真のみ。周辺（海/観光）の写真は原則掲載しない。不足は「画像準備中」
- 徒歩表記は「徒歩約◯◯」のように「約」を付けて掲載する

成果物（ファイル名：まとめる内容）

- docs/CONTENT.md：各セクションの文章（確定/要確認の区別つき）
- docs/FACTS.md：事実データ集（住所/設備/チェックイン等の確定情報、根拠URLや一次情報メモ）
- docs/ASSETS.md：画像/ロゴの一覧（ファイル名、用途、権利確認状況、差し替え予定）
- docs/PROMPTS.md：AI依頼テンプレ集（コピー/構成/レビュー依頼など、前提の固定化）

最初のプロンプト（コピペ用）

```
あなたはシニア相棒エンジニア兼プロダクトエンジニアです。
目的：貸別荘の公式サイトMVPを1週間で公開。
制約：事実の厳守。根拠のない数値は書かない。不明は「要確認」と明示。質問は最大3つ。

次の成果物をMarkdownで作成してください。
1) docs/FACTS.md：住所/チェックイン/アウト/駐車場/設備/最大人数などの「確定情報」だけを整理（根拠や一次情報メモも添える）
2) docs/CONTENT.md：掲載文章をセクション単位で作成し、各項目に（確定/要確認）を付ける
3) docs/ASSETS.md：手元の画像/ロゴの一覧表（ファイル名、用途、alt案、権利確認状況）
4) docs/PROMPTS.md：以後の依頼で使い回せるテンプレ（コピー生成、構成レビュー、文章校正）

入力が不足している場合は、確認質問を最大3つだけ提示してください。
```

## 6. 実装（環境構築→画面→コンテンツ）

実装の順番（迷ったらこの順）

1. リポジトリ初期化（フレームワーク、Lint/Format、基本レイアウト）
2. ルーティング（ページ）と共通コンポーネント（Header/CTA/Footer）
3. セクションを上から順に実装（まずはテキストで埋める）
4. 画像最適化（適切なサイズ、遅延読み込み）
5. SEO最低限（title/description/OGP/favicon）

実装に入る前のゲート（手戻り防止）

- 掲載文言の「要確認」を棚卸しし、公開までに確定できないものは掲載しない（または「要確認」と明示）
- `.env` はコミットしない（`.gitignore` で除外し、値はデプロイ先の環境変数で管理）

公開前チェック（最低限）

- 予約URL（STORES）/公式LINE URL/地図リンクが未設定なら、CTAが「準備中」で無効化されている
- 徒歩表記が「約」付きになっている（断定表現のままになっていない）
- 画像が手元写真のみである（権利不明の第三者素材が混ざっていない）
- Hero画像が横長で綺麗に見える（外観・入口が伝わる）

AI駆動の基本ループ

1. Ask：不明点を最大3つに絞って質問
2. Plan：MVPの範囲・実装順・AC（受け入れ条件）を確定
3. Agent：実装→テスト/確認→ドキュメント更新

成果物（ファイル名：まとめる内容）

- README.md：ローカル起動手順、主要コマンド、デプロイ手順（最低限）
- docs/IMPLEMENTATION.md：アーキテクチャ、ページ/コンポーネント構成、環境変数、外部リンク（予約/地図）
- .env.example：環境変数のキー名一覧（値は書かない・コミットOKな形）

最初のプロンプト（コピペ用）

```
あなたはシニア相棒エンジニア兼プロダクトエンジニアです。
目的：公式サイトMVPを1週間で公開。
制約：過度に複雑にしない。秘密情報はコミットしない（値は環境変数へ）。不明点は最大3つ質問。

次の成果物を作成してください。
1) docs/IMPLEMENTATION.md：推奨アーキテクチャ（例：Next.js + Tailwind等）、ルーティング/ページ方針、コンポーネント分割、外部リンク（予約/地図）、環境変数方針
2) .env.example：必要な環境変数のキー名だけ（例：NEXT_PUBLIC_BOOKING_URL など）
3) README.md：ローカル起動、主要コマンド、デプロイの最短手順

予約URL/地図URL/デプロイ先が未確定なら、差し替え前提の作りにして、確認質問を最大3つ提示してください。
```

## 7. テスト・品質（公開前に落とし穴を潰す）

手動確認チェック

- 表示：スマホ幅（375px）/タブレット/PCでレイアウト確認
- 導線：予約ボタンが機能する、リンク切れがない
- コンテンツ：誤字・価格表の整合・規約の表記
- 速度：画像容量が重すぎない（体感で遅くない）
- アクセシビリティ：画像alt、見出し階層、キーボード操作
- 外部リンク：予約/地図が別タブ遷移するか（必要な場合）

成果物（ファイル名：まとめる内容）

- docs/QA.md：手動確認チェックリスト（表示/導線/コンテンツ/速度/アクセシビリティ/SEO）

最初のプロンプト（コピペ用）

```
あなたはシニア相棒エンジニア兼プロダクトエンジニアです。
目的：公開前の手動確認で致命的な抜けを防ぐ。
制約：チェックは短く実行可能に。不明点は最大3つ質問。

- 端末別（スマホ/タブレット/PC）
- 導線（予約ボタン、リンク切れ）

## 9. 運用（更新手順と改善サイクル）

運用で決めること

- 更新頻度が高い情報（料金、周辺情報、注意事項）の更新手順
- 問い合わせ導線（外部予約/メール/電話など）と対応フロー
- 計測：必要になってから（Cookie利用の有無＝プライバシー要件が変わる）

公開後の改善候補（優先度順）

- 料金の簡易見積（要件が固まってから）
- 周辺スポットのリスト（徒歩分数の根拠込み）
- FAQ/利用規約/プライバシーポリシー整備

成果物（ファイル名：まとめる内容）

- docs/OPS.md：更新フロー（料金/周辺情報/画像差し替え）、問い合わせ対応フロー、改善ログ
- docs/CHANGELOG.md：変更履歴（更新内容/影響範囲/確認項目/ロールバック手順）

最初のプロンプト（コピペ用）

```

制約：運用手順は短く、実行可能に。不明点は最大3つ質問。

次の成果物をMarkdownで作成してください。
