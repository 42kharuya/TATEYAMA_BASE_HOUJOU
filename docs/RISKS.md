# RISKS：TATEYAMA BASE 北条 公式サイトMVP（公開までのリスクと対策）

目的：1週間での公開を止めやすいポイントを先に潰し、手戻りを最小化する。

参照（ソースオブトゥルース）

- 施設・料金の一次情報：docs/INFO.md
- URL未設定時の挙動、画像方針など：docs/DECISIONS.md

## 1. 予約URLが未確定（最重要）

- リスク：公開直前まで `STORES予約URL` が確定せず、CTAが機能しない／誤URLで公開する
- 影響：予約導線の価値が落ちる（MVPの目的に直撃）
- 対策（仕様で潰す）
  - `NEXT_PUBLIC_BOOKING_URL` 未設定時は「準備中」表示＋クリック不可
  - 公開前チェックは「未設定なら準備中で無効化されていること」を必須項目として入れる
- 代替案（運用）
  - 公開当初は「予約は準備中」で開始（URL確定後に差し替えて有効化）

意思決定（2026-03-24）
- STORES 予約URLは公開時点までに用意し、`NEXT_PUBLIC_BOOKING_URL` に設定して有効化する
  - 万一未設定の場合は「準備中」で無効化する（フォールバック仕様）

## 3. 施設の確定情報不足（アメニティ、利用ルール等）

- リスク：アメニティが「未定」のまま、ユーザーが期待/持ち物判断できない
- 影響：問い合わせ増・レビュー低下・トラブル誘発
- 対策（MVP方針）
  - 未確定項目は **掲載しない**（推奨）
  - どうしても必要なら「一般的な案内」ではなく、断定を避けた表現に留める（例：必要物は各自ご持参ください）

## 4. 料金の解釈ブレ（シーズン定義が運用依存）

- リスク：トップシーズン（GW/お盆/SW）など「都度設定」の部分が、サイト上で誤解を招く
- 影響：料金トラブル（差額請求/キャンセル）
- 対策
  - MVPでは「料金表（目安）」として掲載するか、または文言で補足する（例：トップシーズンは期間により変動）
  - 予約は外部（STORES）で最終確定する導線を明示
  - “日付入力の自動計算”はやらない（やるなら仕様とテストが必要）

## 5. 素材不足（写真が足りない/画質が低い）

- リスク：手元写真のみという方針のため、掲載できる写真が不足しやすい
- 影響：訴求力低下、ページが寂しく見える
- 対策
  - 画像がない箇所は無理に埋めず、テキスト中心で成立させる
  - どうしても枠が必要なら「画像準備中」（リンク/外部素材は使わない）
  - Heroは「外観・入口の写真」を主役（DECISIONS準拠）

## 6. 数値表現のリスク（徒歩◯分/秒 等）

- リスク：断定表現による期待ズレ（ルート/信号/歩行速度で変動）
- 影響：クレーム/信頼低下
- 対策
  - docs/DECISIONS.md に従い「徒歩約〜」で統一
  - 一次情報（docs/INFO.md）にない数値は掲載しない

## 7. プライバシー/計測（Cookie、外部サービス遷移）

- リスク：解析タグ導入でCookie同意やプライバシーポリシーが必要になる
- 影響：公開が遅れる／法務リスクが上がる
- 対策（MVP）
  - 解析は“入れない”か、“Cookie不要な最小構成”に限定する（導入するなら要確認）
  - フォームを作らないため、サイト側で個人情報を収集しない設計にする
- 注意
  - 予約（STORES）/問い合わせ（LINE）は外部サービスであり、ユーザーは外部へ遷移する

## 8. ドメイン/DNS/ホスティングでの詰まり

- リスク：ドメイン取得・DNS反映・SSLで想定より時間がかかる
- 影響：公開日の遅延
- 対策
  - 早期に公開先（例：Vercel/Netlify 等）とドメインを決め、疎通だけ先に行う
  - 公開前日ではなく、2〜3日前に本番相当URLで確認する

## 9. 運用・更新の詰まり（料金改定・シーズン追加）

- リスク：料金やシーズン定義の変更が入ると、更新漏れが起きる
- 影響：誤情報の公開
- 対策
  - 一次情報（docs/INFO.md）を更新→サイト反映、という手順を固定する
  - 料金表は“ハードコード”でも、差し替え箇所を一箇所に集約する（実装側の方針）
